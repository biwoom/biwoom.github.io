# Biwoom Obsidian 기반 콘텐츠 구조 개편 개발 가이드

- 문서 버전: v0.11
- 최신 수정일: 2026-11-09
- 대상 프로젝트: Biwoom (OL 코어) (`biwoom/biwoom.github.io`)
- 운영 URL: https://biwoom.github.io/
- 상태: 2026-10-30 로컬 구현. 아래 계획의 기준 시점과 현재 적용 결과를 구분하며, GitHub 업로드·운영 배포는 수행하지 않았다.
- 목적: 사용자가 Obsidian에서 제목과 본문을 작성하고 폴더를 관리하면, Astro가 사이트에 필요한 정보를 자동으로 해석하도록 전환한다.

## 1. 확정된 방향과 범위

1. 현재 `src/content/`를 Obsidian 보관함으로 사용한다. 외부 콘텐츠 폴더나 별도 콘텐츠 저장소로 옮기지 않는다.
2. Vault CMS, Front Matter, Decap CMS는 이번 개편에 도입하지 않는다. 기존 Astro `glob()` 기반 콘텐츠 읽기를 활용한다.
3. 공개 콘텐츠 메뉴는 TEXT, STORY, BLOG 중심으로 축소한다. HOME은 시작 화면 역할을 유지할 수 있으나 별도 콘텐츠 작성 체계로 확대하지 않는다.
4. DESIGN·NET 메뉴와 그 전용 기능을 제거한다. 엔터티와 온톨로지 구상도 이 프로젝트에서 폐지하고 관련 콘텐츠·스키마·조회·UI를 제거한다.
5. TEXT와 STORY 모두 최상위 카테고리를 사용한다. 그 아래는 TEXT의 문헌 → 자료 구분 → 개별 자료, STORY의 series → part → chapter 구조다.
6. TEXT 문헌·문서 화면은 학술형 전용 템플릿을 사용하고, STORY와 Markdown/각주/글자 크기/복사 동작을 공유한다. 자료 구분은 첫 자료로 이동하는 링크이며 실제 탭 패널 전환은 구현하지 않는다.
7. 번역과 연구는 독립적인 자료 묶음이다. 권별 대응 관계나 자동 매칭을 만들지 않는다.
8. 폴더·파일 이름의 숫자 접두어에서 순서를 추출한다. 문서마다 순서 메타데이터를 입력하도록 요구하지 않는다.
9. 불필요한 frontmatter와 데이터 스키마를 함께 정리한다. YAML 없는 새 Markdown 문서가 유효한 작성 입력이어야 한다.

현재 운영 규칙에는 기존 DESIGN·엔터티·태그 규칙 등이 남아 있다. 이 가이드는 합의된 **전환 목표**이며, 현행 구현과 이미 일치한다고 간주하지 않는다. 실제 구현 단계에서 관련 규칙·매뉴얼·스킬을 함께 갱신한다.

## 2. 개편 전 구현에서 확인했던 제약

- `src/content.config.ts`의 TEXT/STORY는 각각 30개 이상의 최상위 필드를 정의한다. 상당수는 선택 사항이지만 실제 문서에도 반복 입력되어 있다.
- `title`은 frontmatter 필수 값이며 BLOG는 `date`도 필요하다.
- `scripts/check-content.mjs`는 공개 TEXT/STORY에 `seriesSlug`를 요구한다. 경로 추론을 추가해도 이 검증을 그대로 두면 새 글을 빌드할 수 없다.
- TEXT/STORY의 시리즈·부·그룹 구성과 순서는 주로 frontmatter를 사용한다.
- STORY의 루트 문서 및 `index`를 시리즈 소개로 판단하는 로직은 새 파일 배치와 충돌할 수 있다.
- STORY 시리즈의 파트 버튼은 해당 파트의 첫 문서로 이동하는 링크다. 아래 파트 목록은 펼침 목록이며 실제 탭 전환이 아니다.
- BLOG 상세 라우트는 `[slug]`다. 폴더 중첩을 지원할 경우 URL 생성과 라우트를 함께 수정해야 한다.
- 자산 동기화는 DESIGN·STORY 중심이며, BLOG에 `design-asset:` 참조도 남아 있다.
- TEXT/STORY 상세 화면, 홈·검색·NET 등에서 엔터티·DESIGN 데이터에 의존하는 코드를 함께 조사해야 한다.
- Obsidian의 `src/content/.obsidian/`가 생성되어 있다. 사용자 설정은 개편 자료와 분리하여 다룬다.

## 3. 콘텐츠 폴더와 계층 해석

```text
src/content/
├── text/
│   ├── 001.중관부/                    # 카테고리
│   │   └── 001.대승현론/              # 문헌 / series
│   │       ├── 001.번역/              # 자료 구분 / part
│   │       │   ├── 001.1권.md         # 개별 문서
│   │       │   └── 002.2권.md
│   │       ├── 002.연구/
│   │       │   ├── 001.대승현론의 성립.md
│   │       │   └── 002.이제설 연구.md
│   │       └── 003.인포그래픽/
│   │           └── 001.1권-다이어그램.pdf
│   └── 002.아함부/
├── story/                            # category → series → part → chapter
│   ├── 001.불전문학/
│   │   └── 010.붓다 스토리/
│   │       └── 010.먼 과거의 서원/001.이야기.md
│   └── 002.선시(禪詩)/
├── media/                            # 공용 자산 / 첫 하위 폴더가 미디어 모음의 분류
├── blog/                             # 날짜 중심 기록
└── .obsidian/                        # 사이트 콘텐츠에서 제외
```

- TEXT·STORY의 최상위 폴더는 카테고리이며 시리즈나 part로 취급하지 않는다.
- 두 메뉴 첫 화면은 `ol-grid-3` 카테고리 카드다. 카드를 누르면 카테고리별 시리즈 목록 페이지로 이동한다. 빈 카테고리도 표시하고, Git 보관이 필요하면 `.gitkeep`을 둔다.
- 자료 구분은 실제 폴더에서 생성한다. 번역·연구·인포그래픽을 고정 enum으로 제한하지 않는다.
- 문헌·파트별 `index.md` 또는 소개용 메타데이터 파일을 필수로 만들지 않는다. 폴더와 자료만으로 목록을 생성한다.
- 소개 문서가 존재할 때만 소개·표지 등을 보완한다. 소개 문서와 일반 문서를 구분하는 예약 이름은 구현 전에 정한다.
- STORY도 카테고리/시리즈/파트/문서 깊이를 사용한다. BLOG에는 이 계층을 강제하지 않는다.
- TEXT의 합의된 계층보다 깊거나 짧은 경로, 루트 독립 문서의 처리는 이관 조사 후 정한다. 기존 문서를 조용히 누락하지 말고 이관 대상으로 보고한다.

### 3.1 숫자 접두어 규칙

- 이름 시작의 `숫자.`를 정렬값과 표시명으로 분리한다. 예: `001.중관부` → 순서 1, 표시명 `중관부`.
- 파일에서는 확장자를 제거한 뒤 같은 규칙을 적용한다. `001.1권.md` → 순서 1, 표시명 `1권`.
- 숫자가 없는 이름도 허용한다. 번호 있는 항목 다음에 숫자 인식 자연 정렬과 한국어 이름 비교를 적용한다.
- 같은 번호는 이름·원본 상대경로 순으로 안정적으로 정렬한다. 중복 번호만으로 콘텐츠를 덮어쓰지 않는다.
- 표시명에서만 접두어를 제거하고 원본 경로는 보존한다. `1권`의 1처럼 제목 자체의 숫자는 제거하지 않는다.
- 같은 파서를 카테고리·문헌·파트·문서에 공유한다. 폴더 순서를 별도 설정 파일에 중복 기록하지 않는다.
- 번호 변경으로 URL이 바뀌지 않도록 URL 정책과 분리한다. 번호 제거 후 식별자 충돌도 검사한다.

## 4. TEXT 화면: 현재 STORY 방식 재사용

### TEXT·STORY 첫 화면

- 카테고리를 접두어 순으로 출력한다. 표시 이름에는 숫자를 노출하지 않는다.
- 카테고리 선택 후 별도 페이지에서 해당 문헌·시리즈 묶음을 보여준다. 상단 버튼 필터는 사용하지 않는다.
- TEXT 문서·첨부자료 개수 집계에 비공개·설정·소개용 보조 파일을 포함하지 않는다.

### 문헌 화면

- 기준 구현: `src/pages/story/[series]/index.astro`.
- 상단 제목·선택적 소개, 자료 구분별 이동 버튼, 구분별 펼침 목록의 구조를 활용한다.
- 자료 구분 버튼을 누르면 **그 구분의 첫 공개 자료로 이동**한다. 같은 페이지의 탭 패널을 교체하지 않는다.
- 번역·연구·인포그래픽 각각의 전체 자료 목록을 펼침 목록으로 보여준다.
- `PART 1` 등 STORY 전용 문구는 TEXT의 자료 구분 의미에 맞게 조정한다.
- 필수 표지·버전·서지정보 입력을 새로 요구하지 않는다. 데이터가 없으면 관련 영역을 생략하거나 폴더명으로 기본 표현한다.
- 빈 폴더에는 첫 자료 링크를 만들지 않는다. 개수와 첫 자료 계산에 Markdown·지원 첨부자료를 같은 규칙으로 포함한다.
- PDF만 있는 구분도 작동해야 한다. 첫 자료 링크는 해당 PDF의 정해진 공개 진입점으로 연결한다.
- 모바일의 펼침 UI와 데스크톱 목록이 같은 자료를 보여주도록 확인한다.
- 공통화할 경우 명시적인 TEXT/STORY 변형을 지원한다. 태그 표시는 `DocumentTags.astro`를 공유한다. 시리즈 태그 모달은 제거하고 BLOG의 태그 분류는 기존 공통 페이지네이션과 결합한다.

## 5. 제목·본문 기반 메타데이터와 스키마 정리

### 5.1 원본과 계산 결과 분리

`src/content.config.ts`는 원본 입력 스키마의 기준으로 유지한다. 입력에서는 YAML을 선택 사항으로 만들되, 페이지가 사용하는 정규화 결과에는 제목·공개 여부·URL·소속 등이 결정되어 있어야 한다.

기존 `glob()`로 읽은 경로·본문·선택적 frontmatter를 공통 처리 계층에서 정규화한다. 본문과 경로를 볼 수 없는 스키마 기본값만으로 이 기능을 구현하려 하지 않는다. 목록·상세·검색·RSS·검증기가 같은 결과와 URL 생성 규칙을 사용하도록 구성한다.

계산 가능한 값을 원본 Markdown에 자동으로 반복 써 넣지 않는다. 전체 사용자 정의 로더는 필요성이 확인될 때만 도입한다.

| 정보 | 목표 처리 |
|---|---|
| 제목 | 이관 중 기존 `title` → 첫 본문 H1 → 번호 제거 파일명. 최종 원본 우선순위는 이관 시 확정 |
| 메뉴·소속 | 경로에서 추출 |
| 카테고리·문헌·자료 구분 이름 | 폴더의 숫자 접두어를 제거한 표시명 |
| 순서 | 폴더·파일의 숫자 접두어 |
| 요약·excerpt | 첫 일반 문단에서 추출, 선택적 수동 설명 허용 |
| 목차·읽기 시간 | 본문에서 생성·계산 |
| 대표 이미지 | 첫 유효 이미지, 없으면 생략. 수동 예외는 선택 사항 |
| 작성자·언어·기본 권리 정보 | 사이트 공통 설정. 기존 개별 권리 예외 보존 |
| 태그 | 선택적 `tags: [수메다, 수밋따]`. 접두어 없음, 상속 없음, 태그 없이 작성·공개 가능 |
| 날짜·공개 여부·고정 주소 | 추론만으로 해결하지 않고 아래 정책 확정 후 구현 |

첫 H1을 페이지 제목으로 사용하면 본문에서 중복 출력하지 않는다. 파일명과 H1을 항상 둘 다 입력하도록 강제하지 않는다. 코드블록·이미지·주석을 요약으로 오인하지 않도록 Markdown 구조를 고려한다.

### 5.2 제거·통합할 필드

- **폐지:** `entities`, `relations`, 엔터티 ID·관계·유형·별칭·지도·외부 ID 및 엔터티 역참조 전용 구조, `OL_ONTOLOGY_VERSION`, ontology 컬렉션 스키마.
- **경로로 대체:** 문서별 `series`, `seriesSlug`, `seriesOrder`, `part`, `partSlug`, `partOrder`, `group`, `groupSlug`, `groupOrder`, 분류용 `category`.
- **번호에서 추출:** `chapter`, `order`. 기존 번호 없는 문서의 순서는 이관 시 파일명에 반영하거나 명시적 예외로 보존한다.
- **통합:** `status`와 `published`의 이중 상태를 제거하고 하나의 공개 모델을 사용한다. 버전·작업 단계는 일반 집필에 필수로 요구하지 않는다.
- **자동 계산:** `readingTime`, `description`, `excerpt`, 기본 이미지 필드는 필요한 예외만 남긴다.
- **단순화:** `tagAliases`와 접두어 태그 강제 규칙을 재검토한다. 엔터티·다국어 분류 관리 부담을 새 체계로 옮기지 않는다. `prefixTags`는 재도입하지 않는다.
- **공통값으로 이동:** `authors`, `lang`, 기본 `license`·권리자. 개별 자료의 라이선스 예외를 일괄 기본값으로 덮어쓰지 않는다.
- **용도 재검토:** `relatedTextCandidates`, `level`, `subtitle`, `version` 등은 실제 화면·집필 용도가 없으면 제거한다.
- **본문으로 이관 가능:** `sources`, `sourceTraditions`, 주석·출전은 작성된 정보를 보존해 본문의 출전·주석 절로 옮긴다. 단순 삭제하지 않는다.

컬렉션별 기존 필드 사용처를 먼저 조사하고, 값을 경로·본문·공통 설정으로 옮긴 뒤 스키마와 소비 코드를 함께 삭제한다. 실제 사용하지 않는 필드를 `.optional()`로만 바꿔 계속 쌓아두지 않는다. `pages`의 방문자용 브랜드 문서는 집필 메뉴 축소와 별개로 취급한다.

### 5.3 설계 시 검토했던 운영 정책

다음은 앞선 논의에서 제안된 항목이며 사용자 확정 사항과 구분한다. 개발 착수 시 최소한의 선택으로 정하고 결정 기록에 남긴다.

- **초안·공개:** `_drafts/` 등 예약 경로로 구분하는 안을 권장한다. 기존 `published: false` 자료가 전환 중 공개되지 않도록 우선 보존한다. 공개 여부를 본문에서 추정하지 않는다.
- **날짜:** BLOG의 기존 날짜를 보존한다. 새 문서의 최초 공개일은 한 번 기록하거나 별도 이력에서 확보한다. 파일 수정 시각·빌드 시각을 공개일로 사용하지 않는다. RSS와 최신순 목록도 같은 날짜를 사용한다.
- **주소:** 폴더 분류·표시명·정렬값과 공개 URL을 분리하는 안을 권장한다. 식별자 자동 생성·별도 매핑 등 보존 방법을 정해야 한다. 내용만 있는 파일의 이동·개명을 식별자 없이 항상 추적할 수 있다고 가정하지 않는다.
- **한글 이름:** 예시처럼 한글 폴더·파일명을 작성 입력으로 허용하도록 기존 ASCII 선호 규칙을 조정해야 한다. 코드 파일·개발 문서 파일명은 ASCII를 유지한다. URL의 한글 사용 또는 자동 식별자 정책은 별도 결정한다.
- **예약 경로:** 소개 문서·초안·첨부파일 이름과 루트 독립 문서·예상 밖 깊이의 처리 규칙을 문서화한다.

## 6. Markdown·PDF·이미지와 내부 링크

- Markdown 컬렉션의 glob 패턴에 PDF를 추가하는 것만으로 해결하지 않는다. 비 Markdown 자료 목록을 별도로 수집해 공통 자료 목록에 합친다.
- 자료 모델은 최소한 자료 유형, 제목, 소속, 순서, 공개 진입 URL을 가진다.
- PDF 제목은 번호·확장자를 제거한 파일명으로 자동 생성한다. 설명용 YAML 파일을 필수로 만들지 않는다.
- PDF 열기·다운로드 또는 자료 소개 페이지 중 진입 방식을 정하고, 목록·첫 자료 링크에서 일관되게 사용한다.
- 이미지·PDF·필요한 기존 HTML 자료를 배포 산출물에 포함한다. 생성 결과는 계속 `public/generated/` 등 파생 경로에 두고 커밋하지 않는다.
- 목록용 원본 PDF와 본문 삽입 이미지 등 보조 자산을 구분한다. 모든 첨부파일을 무조건 개별 문서 카드로 만들지 않는다.
- `.md` 상대 링크를 실제 문서 URL로 변환하고 제목 앵커도 검증한다. 경로 구분·한글·공백·동명 파일을 처리한다.
- Obsidian 위키링크·임베드·블록 참조 지원 범위는 별도로 정한다. 일반 Markdown 링크는 기본 지원하고, 미지원 문법이 자동 호환된다고 안내하지 않는다.
- `.obsidian/`, 템플릿, 초안, 캐시·작업창 설정을 페이지·검색·RSS·자산 배포에서 제외한다. 개인 설정을 일괄 커밋하지 않는다.

## 7. DESIGN·NET·엔터티·온톨로지 제거

### 7.1 제거 대상

- 공개 메뉴와 홈·푸터·검색의 DESIGN/NET 진입점 및 집계.
- `src/pages/design/`, `src/pages/net/`, `src/pages/entity/` 및 전용 라우트.
- `src/content/design/`, `src/content/entities/`, `src/content/ontology/`의 활성 컬렉션과 전용 스키마.

- TEXT/STORY의 Entity 패널·모바일 시트·조회·이름카드 및 관계 참조. 문서 목차는 유지하고 남은 레이아웃을 정리한다.
- DESIGN 전용 자산 resolver·remark 처리·외부 provider 설정은 이관 완료 후 제거하거나 일반 자산 기능으로 통합한다.

### 7.2 삭제 전 이관

1. 기존 DESIGN 원본 이미지·PDF·HTML, BLOG의 `design-asset:`와 `/generated/design/` 참조, 엔터티에서 참조하는 자산을 목록화한다.
2. 유지할 시각자료를 관련 TEXT 문헌의 자료 구분, BLOG 첨부 또는 일반 자산 폴더에 옮긴다. DESIGN 메뉴 제거를 원본 일괄 삭제로 처리하지 않는다.
3. 엔터티의 필요한 설명·출전은 일반 문서나 본문 주석으로 보존한다. 엔터티 데이터베이스·관계 시스템 자체는 남기지 않는다.
4. 기존 링크를 새 주소로 고치고 제거된 페이지의 처리 방식을 정한다. 대응 자료가 없는 페이지를 무관한 페이지로 일괄 이동시키지 않는다.
5. 전용 참조가 사라진 후 파일·스키마·설정을 삭제한다.

`src/pages/book/`, `src/pages/works/`, `atlas`, `ai`, `partners`와 `public/atlas/` 등 잔존·보조 영역도 조사한다. TEXT/STORY/BLOG 중심 목표에 맞춰 제거·이관·유지 목적을 분명히 하되, 사용처 확인 없이 일괄 삭제하지 않는다. 공개 브랜드 페이지와 내부 매뉴얼은 별도 유지 대상이다.

## 9. 단계별 개발 순서

1. **현황 목록과 이관표:** 기존 문서·공개 상태·날짜·순서·URL·자산・권리 정보를 기록한다. 사용자 Obsidian 설정은 건드리지 않는다.

3. **대표 자료 시범 적용:** 한 문헌에 번역 2편, 독립 연구 1편, PDF 1개를 두고 전체 흐름을 확인한다. 별도 필수 소개 문서는 만들지 않는다.

6. **기존 자료 이관:** 본문·권리·날짜·공개 여부를 보존하며 경로·출전·자산을 이동한다. 이관 완료 전 원본 frontmatter를 일괄 삭제하지 않는다.
7. **폐지 기능 제거:** DESIGN/NET/엔터티/온톨로지의 활성 코드를 삭제하고 남은 소비 코드를 정리한다. 임시 호환 처리도 사용처가 없으면 제거한다.
8. **문서·검증 정리:** 규칙·스킬·매뉴얼·컨텍스트를 갱신하고 아래 완료 기준을 확인한다.

2026-10-30에 코드·콘텐츠 이관을 로컬에 적용했다. 구체적인 운영 정책은 아래 적용 결과를 따른다. 당시에는 GitHub 업로드를 수행하지 않았다. 이후 f70b680을 origin/main에 전송했으며 실서비스 배포 완료는 별도 확인하지 않았다.

## 10. 검증과 완료 기준

### 작성·표시

- YAML 없는 제목·본문 문서가 목록·상세 페이지에서 정상 표시되고 제목이 중복되지 않는다.
- 카테고리·문헌·자료 구분이 실제 폴더와 일치한다. 숫자 접두어는 화면에서 숨기고 순서에만 사용한다.
- `001`, `002`, `010`, 번호 없음·동일 번호·한글·공백 사례를 확인한다.
- TEXT의 자료 구분 버튼은 첫 자료로 이동하고, 펼침 목록은 전체 자료를 보여준다. 실제 탭 패널 전환은 없다.
- 번역과 연구의 문서 수·이름이 달라도 독립적으로 작동한다.
- PDF만 있는 구분, 표지·소개·태그 없는 문헌, 빈 폴더를 처리한다.
- 폴더 추가와 새 문서 생성이 개발 미리보기에 반영되는지 확인한다.

### 이관·회귀

- 기존 비공개 자료가 공개되지 않는다. 설정·초안은 검색·RSS·배포 파일에도 포함하지 않는다.
- 기존 날짜·권리·출전·본문·첨부자료가 보존된다.
- 번호 변경·제목 변경·이동 시 URL 동작이 확정 정책과 일치한다. 기존 공개 URL 이관표를 검사한다.
- Markdown 링크·이미지·PDF·남겨 둔 HTML 자료가 빌드 산출물에서도 열린다.
- 활성 코드에서 폐지 컬렉션 조회·스키마·전용 UI 참조가 사라진다. 과거 BLOG의 역사 서술은 무조건 지우지 않는다.
- 남긴 STORY·BLOG·목차·모바일 탐색·공유 필터가 정상 작동한다.

### 실행 검사

- 정규화·정렬·경로 충돌·공개 제외·자산 이관처럼 실패 영향이 큰 규칙은 의미 있는 fixture로 검증한다.
- `npm run check`와 `npm run build`를 실행한다. 실제 카테고리·문헌·문서 경로와 PDF 파일을 `dist/`에서 확인한다.
- 루트 배포를 유지한다. 라우트 변경 시 `astro.config.mjs`, `public/robots.txt`, RSS, sitemap과 기존 URL 처리를 함께 확인한다. Astro `base`를 추가하지 않는다.
- `dist/`, `.astro/`, `node_modules/`, `public/generated/`를 커밋하지 않는다.
- GitHub 업로드와 배포 확인은 사용자가 요청할 때 별도로 수행한다.

## 11. 2026-10-30 적용 결과와 운영 정책

- 제목·본문 기반 입력과 TEXT의 카테고리/문헌/자료 구분 계층, 숫자 접두어 정렬을 구현했다. `001.md`도 순서로 인식하되 H1 제목을 요구한다.
- TEXT/STORY가 같은 시리즈 링크·펼침 목록 컴포넌트를 사용한다. 실제 탭 전환은 추가하지 않았다. 시리즈 태그 모달은 제거하고, 선택적 단순 태그는 개별 문서 제목 아래에 표시한다. BLOG 태그·연도 분류와 공통 더 보기 페이지네이션을 결합한다.
- 공개 폴더의 자료는 기본 공개하며 `_drafts`·템플릿·숨김 폴더를 제외한다. 기존 비공개 값과 시리즈 소개의 비공개 상태를 보존한다.
- `content-registry.json`에 URL·최초 공개 준비일·원본 해시·문헌 경로·이전 주소를 기록한다. 기존 날짜·주소는 유지한다. 새 날짜는 첫 공개 준비 시점이며 파일 수정/매 빌드 시간으로 바꾸지 않는다.
- 폴더·문서 이름 변경은 내용이 같은 경우 자동 추적한다. 개발 서버가 꺼진 동안 이동과 본문 편집을 같이 했거나 동일 내용으로 모호한 경우 `npm run content:move -- old new`로 기존 색인을 연결한다. 완전 자동 이동 추적은 구현 범위가 아니다.
- 한글 작성 경로를 허용했다. URL은 색인에 저장된 주소를 사용한다. 코드와 내부 가이드 파일명은 ASCII를 유지한다.
- `index.md`는 선택적 소개, `assets`/`_assets`는 보조 첨부 경로다. TEXT의 루트 독립 문서는 현재 검증 대상 구조에서 제외하며 카테고리/문헌/자료 구분 위치에 배치한다.
- 일반 `.md` 상대 링크와 `content-asset:` 이관 키를 지원한다. Obsidian 위키링크·블록 임베드는 지원하지 않는다.
- DESIGN 원본과 엔터티 설명은 일반 TEXT 자료로 이관했다. 관련 전용 기능과 스키마·환경 설정은 제거했고 필요한 구주소는 이동 안내로 남겼다. ATLAS HTML은 `.agents/archive/atlas/`에 보존했다.
- 원본 이관표: `.agents/references/content-migration-inventory.json`. 실제 집필 지침은 갱신한 콘텐츠 관리 매뉴얼을 따른다.
- 개발 서버 실행은 로컬 승인 규칙에 의해 거부되어 브라우저 상호작용·라이브 감시는 직접 검증하지 못했다. 콘텐츠·타입·빌드·정적 산출물 검증 결과는 작업 기록에 남긴다.

## 12. 화면 회귀 복구 기준

- 데이터·폴더 개편과 기존 화면 디자인을 분리한다. TEXT/STORY 문서와 BLOG 목록·상세는 기존 마크업·CSS 계약을 유지하며 새 정규화 데이터에 연결한다.
- 검색·모바일 메뉴 같은 공통 기능 CSS는 특정 메뉴의 CSS 안에 두지 않는다. 현재 각각 공통 컴포넌트·레이아웃 스타일에 분리했고 초기 숨김 상태를 HTML에도 명시한다.
- 2026-11-07 사용자 요청으로 TEXT는 새 TextLibrary/TextReader 학술형 템플릿으로 분리했다. 청회색·명조 읽기와 데스크톱 3단/모바일 대화상자를 적용하고, ReaderToolbar/ReaderBody 및 공통 클라이언트 모듈로 STORY와 동작을 공유한다. 카테고리·검색·주소·최초 날짜와 원문은 유지한다. 과거 Entity/독립 파서/구형 TEXT 레이아웃을 복원하지 않는다. BLOG는 전용 템플릿을 유지한다.
- `npm run check:built`는 링크와 정적 UI 마크업·CSS 회귀를 검사한다. 브라우저의 실제 표시·조작 확인과는 별개다.
